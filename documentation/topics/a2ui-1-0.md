# The A2UI 1.0 wire contract

AshA2ui speaks one protocol: [A2UI](https://github.com/a2ui-project/a2ui)
**1.0**. Every message it emits and accepts is a 1.0 message, in both
directions, and there is no version switch. This page is the reference for
the shapes on the wire, for how an action's outcome gets back to the user,
and for what the renderer has to support.

The specification text is `specification/v1_0/docs/a2ui_protocol.md` in the
upstream repository, and its change list from 0.9 is `evolution_guide.md`
beside it. AshA2ui vendors the JSON Schemas, the basic catalog and the
upstream test cases at a pinned commit; `priv/a2ui/v1_0/NOTES.md` records the
pin and the file map.

> #### What is verified {: .info}
>
> - Every message the encoder and the action handler emit in the test suite
>   validates against the vendored 1.0 JSON Schemas (draft 2020-12) and the
>   catalogs they name.
> - The upstream test cases at the pinned commit pass with no exceptions.
> - A few rules the schemas cannot express have their own tests: a single
>   inline `createSurface`, an explicit `value` on every `updateDataModel`,
>   no `returnType` on the wire, UAX #31 names for everything generated.
>
> What is not verified by the Elixir test suite is a browser rendering the
> output on a published renderer release. See
> [What the renderer must support](#what-the-renderer-must-support).

## Messages, agent to renderer

The version string is the bare `"1.0"`. `"v1.0"` and `"v0.9.1"` are invalid.

```json
{"version": "1.0", "createSurface": {
  "surfaceId": "tickets",
  "catalogId": "https://a2ui.org/specification/v1_0/catalogs/basic/catalog.json",
  "components": [ ... ],
  "dataModel": { ... }
}}
{"version": "1.0", "updateComponents": {"surfaceId": "tickets", "components": [ ... ]}}
{"version": "1.0", "updateDataModel": {"surfaceId": "tickets", "path": "/records", "value": [ ... ]}}
{"version": "1.0", "deleteSurface": {"surfaceId": "tickets"}}
{"version": "1.0", "callRendererFunction": {
  "surfaceId": "tickets", "functionCallId": "fc_...",
  "callFunction": {"@call": "downloadFile", "catalogId": "<ash_a2ui catalog id>", "args": { ... }}}}
{"version": "1.0", "agentFunctionResponse": {"functionCallId": "fc_...", "value": { ... }}}
```

What `AshA2ui.Info.build_surface/2` returns is **one** `createSurface` that
carries the whole component list and the initial data model. One paint, one
payload: an HTTP response body or an agent tool result is a single
self-contained message. Data-only refreshes
(`AshA2ui.Info.build_data_model/2`) are a single `updateDataModel`.

Rules the encoder holds:

- `updateDataModel.value` is always present. `null` deletes the key at
  `path`, and an omitted `path` means the root. Region resets are explicit
  whole-value writes (`/form` to its initial shape, `/errors` to `{}`).
- There is no `theme` and no `surfaceProperties`. The protocol leaves visual
  style to the renderer; AshA2ui themes through CSS variables
  (see [Theming](theming.md)).
- A component is `id`, `component` and its properties. The optional
  envelope keys are `@accessibility`, `@checks`, `@catalogId` and
  `@metadata`. The bare forms of those four are invalid.
- A data binding is `{"@path": "/absolute"}` or `{"@path": "relative"}`.
  A function call is `{"@call": "name", "args": {...}}`, with a `catalogId`
  when the function is not in the surface's catalog.
- A `ChildList` template is `{"componentId": "row", "path": "/records"}`.
- Basic-catalog constraints the encoder follows: `Text.variant` is `caption`
  or `body` only, so headings are Markdown (`"## Title"`); `TextField`
  requires `label` and `value`; `Icon.name` is a name, `{"svgPath": ...}` or
  a binding; a check is `{"condition": ..., "message": ...}` where the
  condition is a boolean or a call returning a `ValidationResult`.
- Every generated component id, action name and function name is ASCII
  snake_case, a subset of the UAX #31 identifier classes the catalog schema
  requires.

## Messages, renderer to agent

```json
{"version": "1.0", "action": {
  "name": "submit_form", "surfaceId": "tickets", "sourceComponentId": "submit",
  "timestamp": "2026-11-12T12:00:00Z", "context": { ... }}}
{"version": "1.0", "callAgentFunction": {
  "surfaceId": "tickets", "functionCallId": "fc_...",
  "callFunction": {"@call": "ashAction", "catalogId": "<ash_a2ui catalog id>", "args": { ... }}}}
{"version": "1.0", "rendererFunctionResponse": {"functionCallId": "fc_...", "value": null}}
{"version": "1.0", "error": {"code": "VALIDATION_FAILED", "surfaceId": "tickets", "path": "/components/3/text", "message": "..."}}
```

`AshA2ui.ActionHandler.handle/3` takes any one of these, verbatim, and
returns `{:ok | :error, agent_messages}`. A `version` other than `"1.0"`, a
missing or extra top-level key or a malformed body returns `{:error, []}` and
is logged. `AshA2ui.LiveRenderer` receives each one as the single LiveView
event `"a2ui:message"`.

## How an action's outcome reaches the user

1.0 actions are fire-and-forget: an `action` event has no response of its
own. The protocol's correlated channel is a function call, so AshA2ui
routes every server-handled interaction through one.

The encoder emits each such control (Create, Save, Delete, a pager, a search
box, a bulk action) as a function-call action against the ash_a2ui catalog:

```json
"action": {"functionCall": {
  "@call": "ashAction",
  "catalogId": "<AshA2ui.Encoder.ash_catalog_id()>",
  "args": {
    "name": "submit_form",
    "sourceComponentId": "submit",
    "context": {"values": {"title": {"@path": "/form/title"}}, "recordId": null}
  }
}}
```

The renderer resolves the bindings in `args`, then sends a
`callAgentFunction` with a fresh `functionCallId`. `args.name` and
`args.context` are what an `action` event's `name` and `context` were in
0.9. The agent runs the Ash action, and the handler's reply is a list that
ends with one `agentFunctionResponse` carrying the same `functionCallId`:

- success: `{"value": <the /ui/feedback map>}`;
- failure: `{"error": {"code": ..., "message": ...}}`, where the code is one
  of `VALIDATION_FAILED`, `FORBIDDEN`, `READ_ONLY_AS_OF`, `ACTION_FAILED`,
  `INVALID_ACTION` or `UNKNOWN_ACTION`.

The response goes last, so the data model (field errors, refreshed records,
`/ui/feedback`) is settled before the renderer's promise resolves. A function
other than `ashAction`, or `ashAction` under another catalog id, is answered
with `UNKNOWN_FUNCTION`; a call that fails the argument schema, with
`INVALID_FUNCTION_CALL`.

The encoder never emits `event` actions, and a plain `action` message is
refused: nothing runs, the refusal is logged, and `/ui/feedback` gets an
`UNKNOWN_FUNCTION` error. A renderer drives a surface through the ash_a2ui
catalog's `ashAction` only.

### `/ui/feedback`: one outcome path

Every surface carries one reserved map, initialised in `createSurface`:

```json
"/ui/feedback": {
  "kind": "" | "pending" | "success" | "warning" | "error",
  "message": "",
  "code": "",
  "functionCallId": "",
  "result": {},
  "resultText": ""
}
```

- `kind` `""` is idle. `code` is `""` on success and idle, and the error code
  otherwise.
- The server writes the **whole map** in one `updateDataModel` at
  `/ui/feedback`, never a sub-path, so a stale `pending` cannot survive a
  settled write. It echoes the `functionCallId` of the call it answers.
- `result` and `resultText` carry the output of a map-returning generic
  action, a report or a CSV; the `action_result_text` component binds
  `/ui/feedback/resultText`.
- Field errors stay at `/errors/<field>`.
- The old `/ui/response`, `/ui/action_result` and `/ui/action_result_text`
  paths are gone.

The shipped hook adds the optimistic half. When an `ashAction` call goes out
it writes `{kind: "pending", message, functionCallId}` into `/ui/feedback`
locally, so components bound to it react before the network does. The
server's settled write replaces it. If no response arrives within
`actionTimeoutMs` (default 10 000 ms) and `/ui/feedback` still holds this
call's id, the hook writes a slow notice: still `kind: "pending"`, with
`code: "TIMEOUT"`. The server may still be running the action, so busy
buttons stay busy and nothing invites a second submit; the late outcome
replaces the notice. The pending and slow messages come from the surface's
`/ui/feedback_text` (`pending`, `slow`), which the server writes in the
surface's language.

The quiet actions (`AshA2ui.ActionHandler.quiet_actions/0`: `query`,
`option_search`, `context_search`, `option_select`, `nested_add`,
`nested_remove`, `bulk_select`, `prompt`, `wizard_next`, `wizard_back` and
`open_surface`) report no outcome of their own. The hook writes no pending
state for them, and the server leaves `/ui/feedback` alone unless the action
fails, answering the call with an empty `value`. A page turn, a sort or a
search keystroke therefore never replaces the last outcome or its result.

The hook also dispatches a bubbling
`"ash-a2ui:action-response"` DOM event with
`{functionCallId, surfaceId, response}` for toasts, analytics and optimistic
UI in the host.

## Agent and renderer functions

1.0 has two function channels, and AshA2ui uses one function on each:

| Function | Direction | Used for |
|---|---|---|
| `ashAction` | renderer calls the agent (`callAgentFunction`) | every server-handled interaction above |
| `downloadFile` | agent calls the renderer (`callRendererFunction`) | the CSV export |

An export's `downloadFile` call is the only message of its kind AshA2ui
emits. The renderer answers it with a `rendererFunctionResponse`;
`AshA2ui.LiveRenderer` settles it against the call it pushed and hands the
response to the optional `:on_function_response` callback. See
[Reports and File Export](reports-and-exports.md) for the argument shape.
`AshA2ui.Encoder.call_renderer_function/4` builds the message if you need
another imperative effect; keep it for effects that cannot be data.
Anything expressible as data (status, errors, selection) stays an
`updateDataModel`, which every renderer replays correctly after a
reconnect.

Both functions are declared by the ash_a2ui catalog. `ashAction` sets
`requiresUserActivation`, which makes it `rendererOnly`: only a user gesture
can run a write, and the agent cannot call it. `downloadFile` is
`agentOnly`.

## Catalogs

A catalog declares `"protocolVersion": "1.0"` and refers to the shared
definitions with relative `$ref`s. Functions are keyed `@call`. Catalog
function metadata (`returnType`, `allowedCallers`, `requiresUserActivation`)
lives in the catalog, never on a wire `FunctionCall`.

| Catalog | Where | Components | Functions |
|---|---|---|---|
| Basic | `priv/a2ui/v1_0/catalogs/basic/v1/catalog.json` (upstream, verbatim) | the standard set | the standard set |
| ash_a2ui | `priv/a2ui/v1_0/catalogs/ash_a2ui/catalog.json` | none | `ashAction`, `downloadFile` |
| Admin | `priv/a2ui/admin_v1/catalog.json` | the admin surface components | `openSurface` and others |

The catalog ids are returned by `AshA2ui.Encoder.basic_catalog_id/0`,
`AshA2ui.Encoder.ash_catalog_id/0` and `AshA2ui.Experience.admin_catalog_id`.
An id is a stable URI and need not resolve.

An admin surface's `catalogId` is the admin catalog. The basic components it
uses carry `"@catalogId"` naming the basic catalog, and basic functions
carry `catalogId` in their call. The admin catalog does not re-declare the
basic components it borrows. Where a parent-child relation holds, the admin
catalog states it with `allowedParents` and `allowedChildren`, and a renderer
reports a violation as `UNALLOWED_PARENT` or `UNALLOWED_CHILD`.

A renderer advertises the catalogs it supports in `supportedCatalogIds`;
`AshA2ui.Experience.catalog_for/1` picks the surface's catalog from it.

## What the renderer must support

The renderer packages are `@a2ui/lit` and `@a2ui/web_core`. Their
version-agnostic root entry points carry the 1.0 runtime (the hook imports
nothing from a `v0_9` or `v1_0` subpath):

```javascript
import "@a2ui/lit";
import { Catalog, MessageProcessor } from "@a2ui/web_core";
import { basicCatalog } from "@a2ui/web_core/catalogs/basic/v1";
```

What AshA2ui emits needs a release that implements the specification text at
the pinned commit. Three behaviours matter:

- the `@`-prefixed component envelope keys (`@checks`, `@accessibility`,
  `@catalogId`, `@metadata`);
- `TextField.value` as a required property;
- routing a `functionCall` action whose function no registered catalog
  declares to the agent as `callAgentFunction`.

`@a2ui/lit` and `@a2ui/web_core` 0.15.0 predate all three; their changelog
lists them as unreleased. On 0.15.0, a single component with an
`@`-prefixed key makes the renderer drop the whole `createSurface`. The Hex
package therefore waits for the npm release that implements them. Until
then, run the hook against a build of the upstream renderer at or after the
pinned commit. The shipped hook registers `ashAction` as a JS function in
the ash_a2ui catalog, so the `callAgentFunction` wire is the same either way
and the registration can become schema-only once routing is released.

A renderer must also implement the error contract: report schema failures as
`error` messages (`VALIDATION_FAILED` with `surfaceId` and `path`), which the
handler logs by code, surface, path and call id and never by message text.

### Upstream proposal #4171

Upstream pull request
[#4171](https://github.com/a2ui-project/a2ui/pull/4171) (`@child`, `@action`
and `@functionCall` reserved keys) was open at the pinned commit and is
**not** adopted here. If it merges, `Child`, `Action` and `FunctionCall`
objects take `@` keys, which changes every surface the encoder emits. The
update is a re-vendor of the schemas, a run of the conformance tests and a
change to the encoder; `priv/a2ui/v1_0/NOTES.md` keeps the watch note.

## The executable spec

The test suite is the evidence for the claims on this page:

1. **Upstream cases** (`test/v1_0_conformance_test.exs`): all 178 upstream
   cases, plus the contact-form example, the catalog rules (structure,
   UAX #31 names, restricted `$ref` targets) and the capability and
   data-model payloads, run through `AshA2ui.Test.SchemaHelper` against the
   vendored schemas.
2. **Contract fixtures** (`test/fixtures/v1_0_contract/`): hand-written
   message lists for a table, a form, a board and a wizard, validated by
   `test/v1_0_contract_fixtures_test.exs`.
3. **Encoder and handler tests**: every message they produce is validated
   with the helper, and the semantic rules above have their own assertions.

To re-pin to a newer upstream commit, follow "Re-vendoring" in
`priv/a2ui/v1_0/NOTES.md`. A failing upstream case is a bug to fix, never an
exception to list.
